## 上课节点

- **课前**：五人按本模块交叉核对[规约](11-srs-draft.md)、[用例图](12-use-case-diagram.md)和[矩阵](13-traceability.md)，在草稿 PR 写明核对的编号、异议和验证依据。第二周 #9～13 按原分工继续。
- **课堂 8 分钟讲解提纲**：第 0–1 分钟由组长交代范围与调研样本；第 1–3 分钟由成员 3 沿用例图讲名单和授权；第 3–5 分钟由成员 2、4 走查评分与候选不足；第 5–7 分钟由成员 5 示范版本、撤回与交付；最后 1 分钟组长列出需要裁定的问题。实际主讲人在课后据实登记。
- **课堂评审**：记录教师反馈原意、涉及的需求 ID、结论（通过／需修订）、负责人和期限。其他组提问与教师批准分别登记。
- **课后**：组长把逐项答复、修订 PR、团队复核与教师通过证据回链 #19。对获批提交打 `srs-v1.0` 标签并发布「SRS v1.0」Release，附规约、图、矩阵和变更记录，再进入分析建模。

## 需求变更走 Issue 和 PR

1. 在 Issues 选择「需求变更」。申请人填原需求 ID、触发证据、现有与拟议行为、受影响的用例、验收条件及增量。口头意见先由记录人整理并请提出者核对。
2. 模块负责人检查范围、接口、数据、测试和隐私影响，邀请受影响成员在 Issue 留意见。组长记录批准、退回或延期的依据；影响教师已批基线时再请教师确认。
3. 批准后按协作指南从该 Issue 开分支。PR 同步修改 SRS、图或矩阵中受影响的行、验收标准、故事卡和变更记录。未批准的提案保留在 Issue。
4. 合并后记录 PR、批准人、受影响 ID、版本以及验证证据。正式版本与发布提交一一对应。[协作指南](../CONTRIBUTING.md)

目前仅有第 2 课汇报完成的组长确认。第 3 课讲解、教师评审、签字及正式 Release 各自使用实际记录。
