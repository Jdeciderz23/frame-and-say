# 正式身份与活动邀请方案（待评审）

对应 [#11](https://github.com/Jdeciderz23/frame-and-say/issues/11)，供 #7 以及 #21、#25、#26 后续实现评审。当前代码仍使用受环境限制的双合成身份，本方案不表示正式登录或邀请已经交付。

## 建议采用的登录路径

建议由 Spring Security 的 OAuth2 Login 对接标准 OpenID Connect 提供方：浏览器从后端发起授权，后端处理回调并校验身份，再映射为项目内部用户 ID。提供方及是否需要自建测试服务尚待选型；授权码流程、PKCE 配置、回调地址、state/nonce 与账号绑定应一起验收。

浏览器端建议使用同源的服务端会话，Cookie 设置 HttpOnly、Secure 和合适的 SameSite。采用 Cookie 后，需要为写请求启用 CSRF 防护并实现注销与会话过期，不能直接沿用当前仅接受显式 Bearer 头时的无状态、关闭 CSRF 配置。外部提供方的令牌保存在服务端，前端无需保存长期访问凭据。

具体集成方式需在提供方验证成功后定稿；当前 PR 保持已有 Bearer API 的行为。

## 与现有身份边界衔接

1. 增加内部用户记录，以及外部 `issuer + subject` 到内部用户的唯一映射。显示名和邮箱不作为授权主键，也不凭同名或未核实邮箱自动合并账号。
2. 将 `CurrentActor` 扩展为从已验证的会话身份取得内部用户 ID，业务接口继续不接收“操作者 ID”。
3. 成员模块查询正式账号目录，替换当前依赖 `BootstrapActors.isProvisioned` 的合成账号检查。角色继续属于活动，登录提供方不能直接指定某活动的发起人身份。
4. 正式部署移除演示身份认证路径，保留隔离的测试夹具。当前新增的环境开关只用于限制演示能力，不能替代真实凭据管理。
5. 账号禁用时检查会话与访问状态，管理员的系统职责不自动授予活动照片访问权或代签能力，后续在 #44 验收。

## 邀请建议

首版建议使用一次性随机邀请链接。发起人必须是该活动的组织者；邀请的活动和加入角色由服务端固定，接受请求不能自选活动或提升为发起人。

| 操作 | 建议接口（尚未实现） | 关键结果 |
|---|---|---|
| 创建邀请 | `POST /api/events/{eventId}/invitations` | 只向发起人返回一次随机邀请值；数据库保存摘要、活动、创建者、有效期和状态。 |
| 撤销邀请 | `DELETE /api/events/{eventId}/invitations/{invitationId}` | 发起人可撤销本活动尚未使用的邀请；不能撤销其他活动的邀请。 |
| 接受邀请 | `POST /api/invitations/accept` | 已登录者提交邀请值，服务端确定本人身份；验证状态和有效期后添加为参与者。 |

随机值建议使用至少 32 字节安全随机数；有效期由团队评审后配置，不在本轮硬定。第一位有效接受者原子占用邀请，同一账号重复接受应返回原有成员结果，不产生重复关系；其他账号不能再次使用。已撤销或已过期且尚未使用的邀请不能加入活动。撤销邀请不等于移除已经加入的成员。

不绑定指定账号时，持有有效链接且已登录的人即视为受邀者；是否增加指定账号绑定，由活动与身份维护者结合用户流程确认，并写入验收条件。邀请明文不写入日志或普通成员列表。

实现时新增邀请数据迁移，利用成员关系唯一约束及事务内邀请行锁，原子完成状态校验、成员写入和领取记录。需要覆盖并发接受、重复接受、过期、撤销、跨活动及角色提升的失败请求，不能只依赖前端按钮限制。

| 阶段 | 交付与负责人 |
