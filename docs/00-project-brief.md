# 项目启动说明

项目：**照有商量：基于多用户偏好与公平性约束的协同选片系统**。

英文产品名为 Frame & Say，团队代码托管在公开仓库 [Jdeciderz23/frame-and-say](https://github.com/Jdeciderz23/frame-and-say)。当前工作和调研进度见[项目文档](README.md)，教师立项状态由小组记录。

## 用户、问题和范围

目标用户为大学生旅行、聚餐、班级和社团活动的组织者及参加者。待验证的问题是：照片多、偏好不一致、发布意愿不一致，导致选片反复沟通。

预期主流程为创建活动 → 邀请成员 → 上传照片并由发起人确认出镜名单 → 分别填写偏好和发布授权 → 过滤授权不足的照片并推荐组合 → 解释结果 → 人工确认 → 再检查授权后导出。照片修改产生新版本，需要重新确认该版本的授权。现有 API 和计划中的接口见 [OpenAPI](api/openapi.yaml)。

项目规模限定为单活动 5–10 人、最多 100 张照片。前两周计划交付启动材料、基础工程和五个模块的最小可测试起步，实际完成度按各 Issue 的验收证据记录。

范围内：活动、成员、照片及版本、偏好、发布授权、公平选片、解释、重新确认、确认后导出。

不做：自动人脸识别、AI 美颜、商业交易、社交平台自动发布。拼图不是当前核心需求，暂缓并待团队确认；前两周不安排拼图、批量导出或复杂图片编辑器开发。

## 启动时的工程决策

- 五人均有独立编码责任，同时参加调研、设计、评审、测试和文档工作。
- 前后端同仓库、独立构建。后端采用模块化单体，算法直接用 Java 实现，避免多服务和第二套运行环境。
- 先以 OpenAPI 草案和样例对齐接口，允许前端使用明确标识的模拟数据并行开发。
- 偏好不等于发布授权；任何算法分数都不能越过拒绝或未确认授权。
- H2 只用于基础工程演示和快速测试；业务持久化目标为 MySQL。H2 测试通过不能替代 MySQL 集成验证。
- 文档、接口、代码和测试以 Issue/PR 关联；只记录真实发生的工作。

## 章程与交付增量

小组已确定选题，组长确认第 2 课已完成需求调研汇报。教师立项审核、实际课表和各人投入时间由组长收到记录后更新。[选题 Issue](https://github.com/Jdeciderz23/frame-and-say/issues/20)

采用增量开发。成员访问和照片版本是后续授权的前提，只有授权规则稳定后才能验收推荐和导出。按可使用的业务路径分三次交付，可让五人并行负责模块，并在每次计划、构造、测试和评审后把发现的问题带入下一轮。一次性冻结全部需求会把名单纠错和分享范围的分歧留到联调。按增量评审现有原型的成本较低，身份或授权出现高风险时再做专项验证。

| 增量 | 用户可演示的结果 | 放行证据 |
|---|---|---|
| 1 · 活动相册 | 建活动、加入、上传和浏览私有缩略图 | 两个活动隔离、非法文件拒绝、可重复启动 |
| 2 · 偏好与分享确认 | 分开提交评分与用途授权，修改名单或版本后重新确认 | 比较旧修订和新修订，普通参与者不能确认正式名单 |
| 3 · 公平选片与交付 | 生成可解释的清单，复核后导出 | 固定分歧案例、候选不足、撤回后拒绝交付 |

每一轮结束以 Issue 验收、测试证据、PR 评审和回顾记录判断完成。三个增量是交付范围；各自实际日期以组内排期为准。
